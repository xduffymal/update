# Start here: complete project and demo handoff

This ZIP contains the current application source, templates, CSS, tests, SQL schemas, both saved SQLite databases, public datasets, fitted model versions, official local BERT/CTI-BERT checkpoints, reports, demo inputs and evidence. Extract the ZIP fully before running anything.

## Recommended Windows demo setup

1. Install **Python 3.12, 64-bit** if it is not already installed. The verified environment used Python 3.12.14.
2. Open the extracted `NLP_Project_Full_2026-10-27` folder.
3. Double-click **Start-Demo.cmd**. First setup creates `.venv` and installs `requirements-lock.txt`. This first dependency installation requires internet even though checkpoint files and datasets are included.
4. Choose a password of at least 12 characters when prompted, then confirm it. The script creates a separate demo workspace and account **demo-admin**, and deploys the saved Character TF-IDF email classifier.
5. Open **http://127.0.0.1:5000/lab/** and sign in with **demo-admin** and your chosen password.
6. Keep the terminal open. Press Ctrl+C in that terminal to stop the server.

The checkpoints occupy about 941 MB before compression. Keep `models/`, `data/`, templates and source files together. A virtual environment is not portable and is intentionally recreated on the destination computer. The `.session-key` and `.env` files are excluded. The app generates a fresh session key on startup.

## Equivalent PowerShell commands

Run these from the extracted project folder:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
.\.venv\Scripts\python.exe tools/prepare_demo_workspace.py
$env:LAB_ROOT = Join-Path (Get-Location) 'demo_workspace'
.\.venv\Scripts\python.exe run.py
```

If `demo_workspace` already exists, reuse it and skip the preparation command. To create another disposable demo without overwriting one, run the helper with `--destination demo_workspace_2 --username demo-admin-2`, then point `LAB_ROOT` to that folder. An incomplete failed setup should be preserved for diagnosis and a new destination chosen.

## Run the preserved original workspace

To use `cyber_threat.db` directly instead of a demo copy, open a new PowerShell window in the extracted folder and run:

```powershell
.\.venv\Scripts\python.exe run.py
```

The existing root database has an account, so first-run administrator setup will not appear. Use its existing credentials. A new demo account is created only by the separate demo helper. Both original databases currently have no deployed model. Select one in **Model Management** before expecting learned scanner predictions. The recommended demo helper performs that deployment in the copy automatically.

The normal entry point imports `lab_core.py`, `lab_web.py` and `templates/base.html`. Files ending in `-Mal` are preserved alternate versions. Do not rename or replace the active database simply to follow an old screenshot.

## Run the automated integration tests

```powershell
.\.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider --basetemp=tmp/demo-pytest --junitxml=tmp/demo-junit.xml
```

Use a disposable `--basetemp` directory, because pytest may clear its previous contents. The supplied official MSG fixture is under `tmp/msg-fixtures/unicode.msg`, so the parser acceptance test can run. Tests use fixture databases rather than the two original saved databases.

The optional historical acceptance scripts can generate new versions and need live source access. Run them only in the documented order if required:

```powershell
.\.venv\Scripts\python.exe -m tests.verify_real_models
.\.venv\Scripts\python.exe -m tests.verify_additional_features
```

The second script expects artifacts generated by the first, and includes live external-feed checks. These scripts update the root verification JSON reports and isolated `tmp/real-model-verification` artifacts. Preserve the dated `evidence/` copies for the integration report.
